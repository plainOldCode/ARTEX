# 취약점 다중 트래픽 증거(漏洞多流量证据)

취약점 상세의 「연관 트래픽(关联流量)」은 페이지 간 다중 선택, 용도와 설명, 정렬 및 바인딩 해제를 지원한다. 트래픽 페이지에서도 여러 레코드를 다중 선택해 한 번에 기존 취약점 하나에 연관시킬 수 있다. 작업이 상속한 취약점 증거는 읽기 전용이며, 수정하려면 원본 작업으로 들어가야 한다.

시스템 설정의 「Agent 자동 트래픽 바인딩(Agent 自动绑定流量)」은 기본적으로 꺼져 있으며, 읽기·수정 인터페이스는 `/api/settings`의 `agent_traffic_binding`이다. 켜면 요청/응답 열람, 도구 호출, 프롬프트로 인한 Token 소비가 늘어난다. 다음 라운드의 Agent부터 새 설정을 사용한다. 꺼져 있을 때는 자동 바인딩 파라미터와 보충 바인딩 도구를 숨기고, 자동 바인딩 지침을 주입하지 않으며, 이미 실행 중인 세션이 새로 제출한 자동 바인딩은 거부한다. 수동 바인딩, 트래픽 캡처, 저장된 증거 읽기 및 내보내기는 영향을 받지 않는다.

켠 뒤 기본 흐름은 「발견 후 등록(发现入库) → 자동으로 보고 Agent 트리거 → 트래픽 확인 후 바인딩 → 최신 증거 버전 기준 보고 작성」이다. 보고자는 `evidence`에 검증 명령, 핵심 출력, 기존 실제 트래픽 ID 및 용도를 남긴다. 보고 Agent는 취약점 상세와 실행 기록을 결합해 `traffic_search` / `traffic_get`으로 검증한 뒤 `bind_finding_traffic`을 호출하고, 다시 최신 `version`을 읽어 보고서를 저장한다. 스위치를 끄면 보고 Agent는 원본 트래픽 검색/읽기 도구를 추가로 받지 않고 자동 바인딩도 하지 않는다. 다만 수동으로 바인딩된 스냅샷은 읽고 보고서를 생성할 수 있다.

기존 호출자와의 호환: `report_finding`의 `traffic_refs` / `evidence_hint_id`는 여전히 명시적 즉시 바인딩에 사용할 수 있다. 바인딩은 선택 사항이다. TCP 등 비 HTTP 취약점이거나, 수집되지 않았거나 정확한 레코드를 찾지 못할 때는 참조를 생략해도 정상적으로 보고하고 보고서를 작성할 수 있다. 명령 출력, 로그 등 다른 검증 가능한 증거는 유지하고, 바인딩하지 않은 이유를 설명할 것을 권한다. 필수 필드를 새로 추가하지 않는다. 제출된 ID는 모두 유효하고 본문이 완전해야 한다. 하나라도 실패하면 이번 바인딩 작업 전체가 롤백된다. 보고에 함께 바인딩했다가 실패하면 이번 보고 전체가 롤백된다. 같은 스냅샷을 중복으로 추가해도 바인딩 수가 늘지 않고 설명을 덮어쓰지도 않는다.

## Agent 번호와 보고서 버전

`report_finding`에 선택적 파라미터가 추가되었으며, 배열 순서가 곧 초기 증거 순서다:

```json
{
  "traffic_refs": [
    {"traffic_id": "真实流量ID", "role": "baseline", "note": "正常账户请求"},
    {"traffic_id": "另一个真实流量ID", "role": "proof", "note": "复现请求"}
  ]
}
```

용도는 `baseline`(정상 대조), `proof`(취약점 증명), `verification`(보충 검증), `supporting`(보조 증거, 기본값)이다. 먼저 `traffic_search` / `traffic_get`으로 실제 레코드를 확인한다. 도메인과 시간은 후보 선별에만 쓰이며, 작업 귀속을 추정하지 않는다.

프롬프트는 [CyberStrikeAI의 취약점 보고 도구 지침](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go)을 참고했고, 본 프로젝트의 선택적 바인딩 규약을 결합해 이유 없는 필수 검증을 도입하지 않았다. ID를 추측해서도 안 되고, 보충을 위해 반복 탐지해서도 안 된다.

반환의 첫 줄은 여전히 `finding recorded: <探索节点 ID>`이며, 이어지는 JSON은 독립 취약점 레코드의 `finding_id`, 탐색 노드의 `finding_node_id`, 바인딩 요약을 제공한다.

- `get_finding_traffic(finding_id)`는 **독립 취약점 레코드 ID**를 사용하며, 정렬된 목록과 `version`을 반환한다. `binding_id`, `side=request|response`, `offset`, `length`를 전달하면 분할 읽기가 가능하고, 각 구간은 최대 8192바이트다.
- `update_finding_report`의 `finding_id`는 **계속 탐색 노드 ID를 사용한다**. 새로 추가된 `evidence_version`에는 실제 읽은 버전을 채운다. 생성 도중 증거가 바뀌면 구버전 쓰기가 거부되므로 다시 읽고 생성해야 한다.
- 구버전 보고 호출에서 버전을 전달하지 않으면 기존 트래픽 증거를 덮는다고 주장하지 않는다. 바인딩, 설명, 용도 또는 정렬이 바뀌면 기존 보고서에 갱신 대기 안내가 표시된다.

자동 바인딩을 켜면 `add_hint` / `add_task_hint`가 단일 힌트 또는 배치 `hints`의 각 요소에 `traffic_refs`를 저장할 수 있다. Planner가 대신 보고할 때는 `evidence_hint_id`를 전달해 이 작업에 해당하는 힌트의 참조를 명확히 선택하며, 상속된 힌트는 참조할 수 없다. 시스템은 도메인, 시간, 열람 기록으로 바인딩을 추측하지 않는다. 제출이 실패하면 부분 취약점이 생기지 않고 보고도 조기 트리거되지 않는다.

기존 취약점에 바인딩이 누락되었을 때는 `bind_finding_traffic(finding_id, traffic_refs)`로 보충 바인딩하면 되고, 다시 등록할 필요가 없다. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail`은 명확한 `finding_id`와 `finding_node_id`를 반환한다. 구(舊) `id`는 탐색 노드 의미를 유지한다.

시작 시에는 구(舊) 도구 schema에 선택적 속성만 추가하고, 원본 기본 트래픽 도구 바인딩은 보고 Agent까지 확장된다. 보충 바인딩 도구는 기본적으로 보고 Agent에게 넘어간다. 커스텀 바인딩 목록, 프롬프트, 설명 및 활성 상태는 유지된다. 지침은 최종 도구 조립 후 일괄 추가된다. 보고 역할은 기존 증거의 인수인계를 담당하고, 보고 Agent는 확인, 바인딩, 보고 작성을 담당한다. 플랫폼 대화에 작업 컨텍스트가 없으면 구조화된 힌트로 작업 Agent에게 인계해야 하며 직접 보고하지 않는다. 작업 완료를 판정하기 전에 먼저 기존 증거를 인계해야 한다. 보충 패키지가 없다고 강제로 기다리지는 않는다. 실패한 `report_finding`은 보고 Agent를 트리거하지 않는다.

## API

기본 경로는 `/api/exploration/findings/{finding_id}/traffic`이며 독립 취약점 ID를 사용한다. 기존 인증을 따르고, `context_task`는 작업 가시성과 상속 읽기 전용을 검증한다.

| 메서드 / 상대 경로 | 요청 / 반환 |
| --- | --- |
| `GET` | 정렬된 요약, 증거 버전, 보고서 채택 버전 |
| `POST` | `{"traffic_refs":[...]}` 전체 배치 추가 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"说明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, 전체 목록이어야 함 |
| `GET /{binding_id}` | 스냅샷 메타데이터와 크기 제한 본문 미리보기 |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1`이면 전체 원본 바이트 다운로드 |

버전/정렬 컬렉션 충돌, 아카이브 중 쓰기는 `409`를 반환한다. 상속 쓰기는 `403`이다. 존재하지 않거나 해당 취약점에 속하지 않는 바인딩은 `404`다. 트래픽/첨부 읽기 및 검증 실패는 명확한 오류를 반환한다.

## 저장소와 마이그레이션

시작 시 멱등(idempotent) 마이그레이션으로 PostgreSQL에 `traffic_evidence_snapshots`, `finding_traffic_bindings` 및 `findings.evidence_version` / `report_evidence_version`(기본 0)을 추가한다. 과거 텍스트로 추측해 보충 바인딩하지 않는다.

스냅샷은 원본 트래픽 ID, 수집 시각, URL, 메서드, 상태, 요청/응답 헤더, 본문 길이, SHA-256을 저장한다. 본문은 해시 기준으로 `<data>/evidence/blobs/<前两位>/<hash>.bin`에 저장되며, 정리 가능한 `data/traffic`와 독립적이고 여러 취약점이 스냅샷/본문을 공유할 수 있다. 스냅샷은 내용 갱신 인터페이스를 제공하지 않으며, 검증이 일치하지 않으면 읽기와 내보내기가 실패한다.

원본 트래픽 쓰기 잠금 하에서 대용량 본문 blob과 구(舊) 디렉터리 레코드를 포함한 전체 본문을 읽는다. 먼저 파일을 영속화하고 검증한 뒤, 단일 PostgreSQL 트랜잭션으로 탐색 노드, 의도 관계, 취약점, 스냅샷, 바인딩을 기록한다. 커밋 후에야 플래너에게 알린다. 실패 시 참조 없는 파일이 남을 수 있지만 부분적인 비즈니스 레코드는 생기지 않는다.

PostgreSQL advisory lock `7337741004`가 증거 파일과 SQL 참조를 조율하며, 작업 행 잠금은 아카이브 대기열 등록 이후의 증거 수정을 금지한다. 복구는 본문 설치부터 메타데이터 커밋까지 전 과정에서 증거 잠금을 유지한다. 취약점 삭제는 바인딩을 연쇄(cascade) 제거한다.

정리기는 매시간 실행되며, 참조가 없고 진행 중인 작업에 속하지 않은 내용만 회수하고 최소 24시간 지연시킨다. 일반 트래픽 정리는 증거 디렉터리를 건드리지 않는다. 핫 데이터를 백업할 때는 PostgreSQL과 `data/evidence`를 함께 백업한다.

## 내보내기와 아카이브

Markdown에는 정렬된 증거 목록과 버전이 담긴다. JSON에는 메타데이터가 담긴다. CSV에는 수량과 바인딩 ID가 추가된다. `md-zip`은 취약점 Markdown을 유지하면서 다음을 제공한다:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown은 상대 링크로 패킷을 참조한다. 다운로드 전송 전에 첨부 복사, 해시 검증, 압축, 디스크 동기화 및 전체 ZIP 항목의 CRC 읽기 검증을 완료한다. 누락/손상이 있으면 다운로드 전체가 실패한다. 완전한 첨부는 원본 바이트를 그대로 보존한다.

아카이브 v3는 취약점 바인딩 관계를 기준으로 스냅샷과 본문을 수집하며, 원본 트래픽이나 도메인에 의존하지 않는다. 패키지 검증이 완료된 후에야 핫 데이터를 정리한다. 공유 증거는 계속 보존된다. 복구는 먼저 본문을 검증·설치한 뒤, 트랜잭션으로 메타데이터와 바인딩을 복원하며 실패 재시도를 지원한다. v1/v2도 계속 복구 가능하고, 누락된 새 필드는 명시적으로 0으로 채운다.

## 검증과 경계

각 테스트 패키지마다 독립적이고 새로 만든 PostgreSQL 테스트 DB를 `ARTEX_PG_DSN`으로 지정해, 잔존 작업/모델 fixture가 백그라운드 실행을 트리거하지 않도록 한다. 관련 패키지의 전체 테스트를 실행하고, 설정 누락으로 인한 skip이 없음을 확인한다:

```sh
# 每个包运行前将 ARTEX_PG_DSN 设为对应的独立测试库；显式配置失败必须报错。
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

프런트엔드 검증에는 `npx tsc --noEmit`, 영향 받는 파일의 Biome 검사, Webpack 빌드, `NEXT_EXPORT=1` 정적 내보내기가 포함된다. 독립 캐시 디렉터리를 사용해 실행 중인 개발 서비스를 덮지 않는다.

로컬 엔드투엔드 인수 검수는 독립 포트, 통제된 HTTP / 도메인 HTTPS 대상, 임시 데이터 디렉터리를 사용해 두 바인딩 진입점, 페이지 간 선택, 정렬/설명, 오류 안내, 상속 읽기 전용, 다운로드, 그리고 원본 트래픽 삭제 후 내보내기, 아카이브, 핫 본문 회수, 복구 및 해시 검증을 커버한다.

첫 버전은 전역 증거 조율 잠금을 채택했다. 대규모 바인딩/내보내기 또는 느린 첨부 다운로드 도중에는 다른 증거 작업이 대기할 수 있다. 녹화 레코드나 완전한 본문이 없으면 증거를 임으로 만들어낼 수 없다. 본 기능은 캡처 스위치를 바꾸지 않으며, HTTPS로 IP를 직접 방문할 때의 인증서 문제도 다루지 않는다.
