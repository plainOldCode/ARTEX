## [Unreleased]

### 차단

#### 새로운 기능

- **내장 차단 규칙 「삭제류 API 경로」 추가**: 기존 내장 HTTP 파괴적 규칙은 DELETE **메서드**(`curl -X DELETE`, `requests.delete(`, `method:'DELETE'`)만 인식했고, 경로류 규칙의 단어 목록은 `/clear /wipe /flush /purge /truncate /drop /destroy /factory-reset /reset-all`뿐이었다. 그런데 대부분 애플리케이션의 삭제 API는 GET/POST로도 트리거되므로, `curl 'http://t/api/user/delete?id=1'` 같은 호출은 어떤 내장 규칙에도 걸리지 않아 대상 데이터를 실제로 지워버린다. 이제 `/delete /del /remove /unlink /erase /destroy`를 커버하는 `deny` 규칙을 하나 보충한다(`/deleteAll`, `/delete_user`, `/delete-user` 같은 접미 형태는 허용). 동사 뒤에는 반드시 구분자가 따라와야 하며, `/delivery`, `/details`, `/delta`, `/delegate`는 오차단되지 않는다. 이 규칙은 독립된 시드 플래그로 배포되어 **기존 인스턴스도 업그레이드 후 획득**한다. 나머지 내장 규칙과 마찬가지로 「시스템 → 명령 차단(命令拦截)」에서 비활성화하거나 삭제할 수 있다.
### 취약점 푸시

#### 새로운 기능

- **취약점 발견을 IM으로 푸시**: 「시스템 → 알림 푸시(通知推送)」 페이지가 새로 추가되어, 스캔 발견을 **딩딩톡(钉钉), 페이슈(飞书), 위챗 워크(企业微信), 범용 Webhook, Telegram, 메일** 여섯 가지 채널로 푸시할 수 있다. 동일 유형에 로봇 인스턴스를 임의 개수만큼 구성할 수 있고(예: 「긴급 대응 그룹」「일일 브리핑 그룹」에 각각 딩딩톡(钉钉) 봇 하나), 각 인스턴스는 시작/정지, 속도 제한, 필터 규칙을 독립적으로 설정한다.
- **푸시 시점을 실시간과 요약 두 가지 모드로 구분**: 실시간 모드는 적중 즉시 건별 전송. 요약 모드는 전역 주기(기본 30분)마다 한 배치의 취약점을 한 메시지로 합쳐, 머리말에 「최근 N분 신규 취약점 M건」과 심각도 분포를 제시해 즉시 처리가 필요한지 한눈에 판단하게 한다. 「고위험만 실시간, 나머지는 요약」으로 운영하려면 채널을 둘 만들어 각각 설정하면 되며, 정책을 코드에 박아두지 않았다.
- **필터 규칙은 네 가지 차원 지원**: 최저 심각도, 작업 / 자산 범위 제한, 취약점 유형 키워드 포함·제외(제외 우선), 그리고 처리 상태 변경 수신 여부(기본값은 꺼짐 — 다수의 사람이 말하는 「푸시」는 상태 변경 기록지가 아니라 신규 취약점 발견을 의미하기 때문). 개별 메시지에는 「상세 보기」 버튼이 붙어 취약점 상세로 이동하며, 대상 주소는 전역 「되돌리기 주소(回链地址)」 설정으로 결정되고 비워 두면 버튼이 붙지 않는다.
- **전송 이력과 수동 재전송**: 알림 페이지에는 각 전송의 상태, 시도 횟수, 실패 사유와 소속 채널이 표시되며 채널·상태별로 필터링할 수 있다. 실패 항목은 원클릭 재전송이 가능하다(재전송은 재시도 카운트를 0으로 초기화한다 — 사람이 직접 재전송을 눌렀다는 것은 실패 사유가 이미 처리되었음을 의미하기 때문).
- **채널 자격증명 마스킹 회돌이**: Webhook 주소, 서명 키, Bot Token, SMTP 비밀번호 등은 각 채널이 자체 선언하고(`SecretKeys()`), API는 끝자리 힌트가 붙은 마스크 값만 회돌이한다. 제출 시 마스크 값을 그대로 돌려보내면 「수정 없음」을 뜻하며, 입력창을 비우면 해당 필드가 삭제된다.

#### 수정된 문제

> 이 절은 기능 초기 버전 완성 후 한 차례 보안 감사의 결론을 기록한다. 각 항목은 재현 → 수정 → 회귀 테스트 보충의 순서로 진행되었다.

- **「대상 주소 변경·자격증명 유지」로 마스킹을 우회할 수 있는 문제 수정(심각)**: 마스킹 메커니즘의 목적은 「자격증명을 브라우저에 회돌이하지 않는 것」이지만, 대상 주소와 자격증명은 서로 독립된 두 필드이고 설정 병합은 「언급되지 않은 키」의 DB 원래 값을 무조건 유지한다. 그 결과 **주소만 바꾸고 자격증명은 언급하지 않는 것만으로** 서버가 DB의 진짜 자격증명을 임의의 주소로 보내게 된다 — 범용 Webhook의 `Authorization` 헤더, Telegram의 Bot Token(요청 경로에 들어감), 메일 채널의 SMTP 비밀번호(STARTTLS 후 상대에게 전달)가 모두 유출되며, 완전히 침묵하고 리다이렉트에 의존하지도 않는다. 이 경로는 실측으로 가능함이 확인되었고 네 채널에서 하나씩 재현되었다. 이제 규정은 다음과 같다: **대상 주소가 변경되면 호출자는 모든 자격증명 필드에 대해 명시적으로 입장을 밝혀야 한다**(새 값을 주거나, 더 이상 필요 없음을 명시적으로 빈 값으로 표현) — 마스크 값을 그대로 돌려보내는 것은 「기존 자격증명 유지」와 같으며 바로 그 공격 형태이므로 함께 거부한다. 「자격증명 자동 폐기」는 의도적으로 만들지 않았다. 선택적 자격증명 필드(예: `headers`)에서 그렇게 하면 「인증이 조용히 사라졌는데 API는 성공을 반환」하는 상태가 되어 오류보다 원인 파악이 더 어렵기 때문이다.
- **markdown 계열 채널이 신뢰할 수 없는 콘텐츠를 전혀 이스케이프하지 않던 문제 수정**: 딩딩톡(钉钉), 위챗 워크(企业微信), 페이슈(飞书) 세 채널은 이전까지 이스케이프를 전혀 하지 않았다(Telegram과 메일은 했다). 취약점 제목과 요약은 모델 출력에서 온다(모델이 읽는 것은 피대상의 응답이다), 자산의 `url`은 스캔에서 얻은, 대상이 조작 가능한 쿼리 문자열을 포함한 완전한 URL이다. 제목이 `登录口 SQL 注入\n[紧急：点此验证账号](http://attacker.tld)`인 취약점은 보안 엔지니어의 딩딩톡(钉钉)/페이슈(飞书)에서 **클릭 가능한 외부 링크**로 렌더링되고, `![](http://attacker.tld/beacon)`은 렌더링 시 클라이언트가 페치한다 — 「이 취약점은 이미 열람되었다」고 통보하고 열람자의 IP를 유출하는 셈이다. 이제 단일 행화 + markdown 메타문자 이스케이프를 통일 적용한다. 아울러 관련 설계 오류 하나도 수정했다: 이스케이프는 각자의 렌더링 출구에서 이루어져야 하며, 네 가지 문맥이 공유하는 제목 함수에 넣어서는 안 된다(markdown 이스케이프가 Telegram의 HTML에 새어 나가면 눈에 보이는 백슬래시가 남는다).
- **전송 주소의 SSRF 공격면 수정**: 이전에는 scheme과 host만 검증하여 `169.254.169.254`(클라우드 메타데이터, 인스턴스 자격증명을 읽을 수 있음), 루프백 주소, 내부망 주소도 모두 전송 가능했다. 또한 전송 실패 시 응답 본문 앞 200바이트가 `last_error`에 들어가 전송 이력 API로 회돌이되므로, 반맹 읽기 원시기(임의 내부망 HTTP 엔드포인트 응답의 앞 200바이트를 읽을 수 있음)가 성립했다. 이제 **다이얼 단계**에서 방어한다(설정 저장 시에만 검증하는 것이 아니라) — 최종 적용점은 거기이며, DNS 리바인딩과 동일 호스트 리다이렉트를 동시에 커버하고, 호스트 간 리다이렉트는 거부한다(이들의 자격증명은 URL 안에 있으므로 리다이렉트를 따라가는 것은 대상에게 넘겨주는 것과 같다). 루프백과 링크 로컬 주소는 `ARTEX_NOTIFY_ALLOW_LOCAL=1`을 명시 설정해야 통과한다(로컬 SMTP 릴레이는 합법적 구성이므로 일괄 금지할 수 없다). **RFC1918 사설망은 의도적으로 통과**시킨다. 내부망 자체 구축 Mattermost / SMTP 릴레이가 흔하고, 그 수준까지 방어하면 정상 배포까지 망가지기 때문이다.
- **푸시 자격증명이 오류 메시지로 외부 유출되는 문제 수정**: 전송 실패 시 `http.Client.Do`가 반환하는 `*url.Error`는 **완전한 URL**을 오류 텍스트에 넣는데, 딩딩톡(钉钉)의 `access_token`, 위챗 워크(企业微信)의 `key`, 페이슈(飞书)의 hook id, Telegram의 `/bot<token>/`은 **모두 URL 안에 있다**. 이 문자열은 네 출구로 흘러들었다: `notification_deliveries.last_error`에 평문 저장, 전송 이력 API의 원상 회돌이(채널 설정의 마스킹을 우회), 서버 로그, 테스트 전송 API가 프런트에 돌려주는 오류 안내. 이제 통일 마스킹 — 오류 메시지는 `scheme://host`와 하위 원인만 남긴다(DNS / 연결성 / 인증서 문제를 찾기에 충분), 경로와 쿼리는 일괄 버린다. 주소 검증 자체(`url.Parse` 실패)의 오류 텍스트도 완전한 주소를 담고 있어 같은 처리를 적용한다. **이전 라운드에서는 전자만 고치고 후자를 놓쳤으며, 당시 회귀 케이스는 전부 scheme 분기를 통과했을 뿐 파싱 실패 경로를 전혀 커버하지 못한 가짜 보장이었다** — 이제 해당 분기를 실제로 커버하는 케이스를 보충했다.
- **요약 메시지가 잘린 뒤 전 배치가 전송 완료로 표시되어 조용히 유실되는 문제 수정**: 채널마다 길이 상한이 있고(위챗 워크(企业微信)의 4096바이트가 가장 빡빡하다), 한 배치가 들어가지 않으면 메시지가 잘리는데, 전송 성공 후 전 배치 전송이 전달 완료로 표시된다 — 잘린 항목들은 **메시지에도 없고 실패 목록에도 없으며**, 전송 이력에는 성공으로 표시되어 취약점이 그냥 사라진다. 이제 **통(條) 단위**로 묶는다: 이번 메시지에 담긴 것만 전달 완료로 표시하고 나머지는 큐로 돌아가 다음 메시지에서 계속 보내며, 메시지 머리에 「이번 메시지에는 앞 N건 표시, 나머지 M건은 다음 메시지에서 계속」이라고 사실대로 적는다. 연기된 항목은 **재시도 횟수를 소모하지 않는다**(수령 시 낙관적으로 +1한 것을 되돌린다). 그렇지 않으면 500건 적체가 세 번째 구간에서 꼬리 항목을 실패로 판정한다 — 한 번도 오류를 내지 않았는데도.
- **최저 심각도 문턱 오타로 필터가 조용히 무효화되는 문제 수정**: `min_severity`를 `hgih` 같은 오타로 쓰면 미지 레벨은 서수표에서 0이 되어 판정이 `rank >= 0` 항상 참으로 퇴화한다 — 사용자는 「고위험만」으로 제한했다고 믿지만 실제로는 모든 취약점이 그룹에 쏟아지고, 화면상으로 설정이 올바른 경우와 완전히 구분되지 않는다. 이제 쓰기 경로에서 값을 검증하고, 오류 메시지에 선택 가능한 값을 나열한다(읽기 경로는 여전히 관대하게 유지: DB에 이미 있는 나쁜 값 때문에 채널 전체를 읽지 못하게 하지 않는다).
- **`rate_per_min = 0`(속도 제한 없음)에 도달할 수 없던 문제 수정**: 문서, 화면 안내, 토큰 버킷은 모두 0을 「제한 없음」으로 해석하는데, 유일하게 DB 쓰기 계층에 `if RatePerMin <= 0 { 取默认值 }`(기본값 사용)이 있어 명시적 0을 몰래 20(钉钉/企微/Telegram) 또는 100(飞书)으로 바꿔버린다 — 조작자는 제한을 풀었다고 생각하지만 실제로는 막혀 있고 어떤 안내도 없다. 「미지정」과 「명시적 0」의 구별은 요청 본문으로만 표현할 수 있으므로, 기본값은 API 계층에서 필드가 생략될 때 채우도록 옮겼다.
- **요약 채널이 토큰 버킷을 완전히 우회하던 문제 수정**: `allow`는 `takeTokens`가 차감해 놓고 아무도 사용하지 않았고, `rate_per_min`은 digest 모드에 아무 효과가 없었다. 이제 수령 건수는 「이번 라운드 할당량」과 메모리 상한 두 제약을 동시에 받는다.
- **실패 처분을 배치 최대 시도 횟수로 판정해 오래된 전송이 신규 전송을 연좌시키던 문제 수정**: 배치 내 각 항목의 시도 횟수는 다른데, 두 번 재시도한 오래된 전송이 같은 배치의 완전히 새로운 전송을 함께 failed로 끌고 들어간다 — 신규 취약점이 재시도를 한 번도 쓰지 못하고 영구 유실되며, 「오래된 행이 새 행을 물에 끌어들이지 않는다」는 원래 의도와 정반대다. 이제 건별 판정: 영구 실패는 즉시 사망, 각자의 재시도 횟수가 소진되면 사망, 나머지는 각자의 백오프 단계에 따라 재정렬.
- **요약 배치에서 스냅샷을 파싱할 수 없는 전송이 조용히 성공으로 표시되던 문제 수정**: 이런 항목은 렌더링 단계에서 건너뛰어지지만(배치 전체를 망치지 않기 위해), 이후 배치 전체가 전달 완료로 표시되며 함께 성공으로 계산된다. 이제 명시적으로 실패로 판정하고 사유를 제시하며, 전송 이력에서 조회할 수 있다.
- **단일 채널의 라운드당 전송 건수가 임대 시간을 초과할 수 있던 문제 수정**: 임대는 3분인데, 한 라운드에서 직렬 전송 가능한 건수가 최악 소요시간이 임대를 초과할 만큼 많으면 다중 인스턴스 배포에서 상대가 임대 만료 행을 다시 수령해 중복 전송하고 시도 횟수를 두 배로 증가시킨다. 이제 「임대 / 단일 타임아웃」으로 라운드당 상한을 역산하고, 세 상수의 관계를 고정하는 단정문이 하나 있다(이 단정문을 쓰면서 기존 값 6이 정확히 임대를 꽉 채우고 여유가 0임을 즉시 발견해 5로 조정했다).
- **Telegram 잘림이 HTML 엔티티를 끊을 수 있던 문제 수정**: 잘림 처리는 반쪽 태그만 피했고 `&amp` 같은 잘린 엔티티 잔해는 피하지 않았으며, 파서가 그 때문에 **메시지 전체**를 거부할 수 있다 — 초장문 요약 메시지는 원래 흔하므로 대가가 너무 크다. 이제 미닫힘 태그와 엔티티 잔해를 동시에 회피한다.
- **메일 채널이 일시적 SMTP 실패를 영구 실패로 판정하던 문제 수정**: SMTP의 4xx(예: 그레이리스트 `450`)는 임시 거부이고 정석은 나중에 재시도하는 것인데, 이전에는 모두 영구 실패로 판정했다 — 그레이리스트를 켠 메일 서버 하나만으로 **모든** 푸시가 첫 시도 후 실패로 떨어지며, 이는 바로 자동 재시도가 가장 힘을 발휘해야 할 상황이다. 이제 응답 코드 첫 자리로 구분: 4xx는 재시도 가능, 5xx는 영구 실패, 코드를 못 얻으면 재시도 가능으로 처리.
- **중첩 구조 제출 시 마스크 리터럴이 실제로 DB에 기록되던 문제 수정**: `webhook.headers` 같은 객체 필드는 통째로 마스킹하거나 통째로 제출해야 한다. 마스크 센티넬을 객체 내부에 넣으면 「변경 없음」도 표현할 수 없고 실제 값으로 저장되어 이후 인증이 조용히 무효화되고 어떤 오류도 없다. 이런 제출은 이제 명시적으로 거부된다.

#### 설계 노트

- **취약점 기록 트랜잭션은 블라인드 INSERT를 한 번만 수행**: `notification_events`는 `RecordFindingTx`가 **동일 트랜잭션** 안에서 기록하며, 커밋은 「취약점 DB 반영」과 「푸시 작업 존재」의 원자적 일치를 보장한다. 이 INSERT는 의도적으로 채널 테이블을 읽지 않고 사용자 필터 규칙도 실행하지 않는다 — 그렇지 않으면 잘못 설정된 필터 조건 하나가 트랜잭션을 오염하거나 중단시켜 고위험 취약점이 DB에 저장되지 않을 수 있다. 실패를 이 한 문장으로 격리하기 위해(PostgreSQL에서 트랜잭션 내 임의 문장의 오류는 트랜잭션 전체를 무효화하여 `COMMIT`마저 실패하게 한다), `SAVEPOINT`로 감싸고 실패 시 로그만 남기며 취약점 기록에 영향을 주지 않는다.
- **전송은 장기 트랜잭션이 아닌 임대 수령 방식**: `FOR UPDATE SKIP LOCKED`로 수령한 뒤 행을 `sending`으로 두고 `next_attempt_at`을 미래로 밀어 임대로 삼는다. 트랜잭션을 커밋한 후에 네트워크 전송을 하므로 전송 중에도 DB 잠금을 쥐지 않는다. 프로세스 크래시가 남긴 `sending` 행은 임대 만료 후 다음 라운드에서 다시 수령되어 자가 치유되며 무한 재시도를 만들지 않는다.
- **속도 제한은 재시도 예산을 소모하지 않음**: 엔진은 먼저 채널 토큰 버킷으로 이번 라운드에 보낼 수 있는 건수를 계산한 뒤 그 수만큼 수령한다. 순서를 뒤집으면(먼저 수령 후 버림) 속도 제한에 걸린 전송이 시도 횟수를 헛되이 한 번 차감되고, 세 번의 예산이 순수한 대기로 소진된 뒤 실패로 떨어진다. 초과분은 메시지를 잃지 않고 전송을 다음 tick으로 미룰 뿐이다.

### 테스트 인프라

#### 수정된 문제

- **기업 ICP 소속 케이스의 정리 순서로 인한 자산 영구 잔존 문제 수정**: 이 케이스의 정리는 `t.Cleanup`에 등록되어 있지만 연결 종료는 `defer d.Close()`로 처리 — `defer`는 함수 반환 시 먼저 실행되고 `t.Cleanup`은 그 뒤에 실행되므로, 정리 문장이 전부 **이미 닫힌 연결** 위에서 실행되고 오류는 `_, _ =`로 버려져 테스트 자산과 기업이 DB에 영구 잔존한다. 이 케이스는 `MAX(companies.id)+1`을 가짜 TaskID로 써 자산에 태깅하는데, 이 숫자가 다른 케이스의 작업 id와 충돌하면 「정확히 N개 자산」을 단정하는 케이스가 원인 불명으로 실패하고 위치를 잡기가 극히 어렵다. 이제 연결 종료도 `t.Cleanup`으로 진행하되 앞서 등록하고(후입선출로 정리가 먼저 실행됨을 보장), 정리 실패가 삼켜지지 않고 드러나게 한다. 같은 패턴(`defer d.Close()` + `t.Cleanup`에서 DB 기록)은 `db` 패키지에 십여 곳 더 있지만, 이번에는 실증적으로 트리거된 한 곳만 고쳤다.

### 트래픽

#### 새로운 기능

- **트래픽 목록에 「전체 비우기」 추가**: 트래픽 기록 전체를 한 번에 삭제하고 현재 필터 조건을 무시하며, 인덱스가 더 이상 기록하지 않는 과거 host 디렉터리도 추가로 정리해 잔여를 남기지 않는다. 비운 뒤 전체 압축(`optimize` + `VACUUM` + `wal_checkpoint(TRUNCATE)`)을 한 번 수행해 인덱스가 점유한 디스크 공간을 시스템에 돌려주고, 완료 후 실제 해제량을 알려준다. 취약점에 결합된 트래픽 증거는 독립된 증거 DB에 보관되며 영향을 받지 않는다. 빈 DB에서의 `VACUUM`은 비용이 거의 없으므로, 이는 동시에 **기존 인스턴스가 인덱스 DB를 증분 회수 모드로 전환하는 경로**이기도 하다 — 한 번 비운 뒤에는 일상적인 host별 삭제만으로 공간이 스스로 회수된다.

#### 수정된 문제

- **트래픽 삭제 후 디스크 공간이 회수되지 않던 문제 수정**: 삭제는 데이터를 보이지 않게 할 뿐 공간은 인덱스 파일에 그대로 남는다. SQLite의 행 삭제는 페이지를 freelist에 붙일 뿐이고 인덱스 DB는 생성 시 `auto_vacuum`이 켜지지 않아 파일이 영원히 줄지 않는다. 또한 `ex_fts`는 `contentless_delete` 전문 인덱스로, `DELETE`는 tombstone만 기록하고 원래 postings를 회수하지 않아 병합하지 않으면 영구 누적 — 트래픽을 지우면 오히려 인덱스가 커진다. 256KB 이하 본문은 전부 이 DB에 인라인되고 trigram 인덱스가 본문 부피의 약 2배에 이르므로, 캡처량이 큰 인스턴스는 이미 삭제된 트래픽을 위해 배수의 디스크를 장기 점유한다(실측: 6MB 본문 캡처 → 인덱스 16MB, 전부 삭제 후에도 16MB). 이제 새로 생성하는 인덱스 DB는 `auto_vacuum=incremental`을 바로 활성화하고, 매 삭제 커밋 후 백그라운드에서 블록 단위로 「전문 인덱스 증분 병합 + `incremental_vacuum` + `wal_checkpoint(TRUNCATE)`」를 실행해 점차 공간을 OS에 돌려준다(동일 시나리오에서 삭제 후 104KB로 회귀). 회수는 블록 단위로 진행되고 블록 사이에 쓰기 잠금을 해제해 트래픽 녹화를 막지 않는다. 프로세스 종료 시 즉시 양보하고 남은 작업은 다음 삭제 때 이어서 한다.

> 업그레이드 안내: `auto_vacuum`은 DB 생성 시에만 설정할 수 있으므로 **기존 인스턴스의 인덱스 DB는 여전히 구 모드**이며, 그 위에서 `incremental_vacuum`은 아무 동작도 하지 않는다 — 시작 시 한 줄 안내를 출력한다. 이런 DB는 업그레이드 후 tombstone의 지속 증가는 멈췄고(전문 인덱스 병합은 평소대로 실행), 이미 점유된 부피는 트래픽 목록의 「전체 비우기」로 한 번 회수하면 된다 — 그 단계가 DB를 증분 회수 모드로 전환하며, 이후 일상 삭제가 스스로 적용된다.

### LLM

#### 수정된 문제

- **커스텀 세션 헤더가 「일회성 LLM 호출」 경로에서 적용되지 않던 문제 수정**: 세션 헤더의 값은 요청 context의 session id에서 가져오는데, 이 id는 agentcore가 transcript store를 마운트한 경우에만 context에 기록한다. 목표 분해(0라운드)와 콜드 노드 압축(§4 body 호출)은 모두 store 없는 일회성 호출이라 context에 session id가 없고 게이트웨이 쪽에서 이 헤더를 읽지 못한다. 「`x-opencode-session`이 없으면 곧바로 400 MissingSessionID」를 내는 opencode zen류 엔드포인트에서는 「0라운드 목표 분해는 400 실패, 이후 planner 라운드는 완전히 정상」으로 나타나며, 압축 실패는 한 줄 로그만 남아 연관 짓기가 극히 어렵다. 이제 이 두 경로에 탐색별로 안정적인 session id(`exp<N>-goals` / `exp<N>-compactor`)를 명시적으로 단다. 헤더를 정상적으로 실을 수 있고, llmrec도 이 두 경로의 token 사용량을 해당 탐색에 정확히 귀속시킬 수 있다(이전에는 전혀 기록되지 않았다).

### 발견

#### 수정된 문제

- **「자산별」 뷰의 자산 목록이 넘친 뒤 스크롤바가 없던 문제 수정**: 왼쪽 자산 트리에는 이미 스크롤 컨테이너가 씌여 있었지만 바깥 카드는 `max-height`만 주고 확정 높이가 없어, 스크롤 뷰포트는 `height:100%`로는 높이를 해석하지 못한다(CSS에서 `max-height`만 설정하고 `height`가 `auto`로 남으면 백분율 높이가 적용되지 않음). 그래서 자산이 많으면 목록이 카드를 뚫거나 잘리고 스크롤도 불가했다. 이제 높이 상한을 자산 트리의 네이티브 스크롤 컨테이너에 직접 걸고(`overflow-y-auto` + `max-h`, 창 높이에 맞춰 적응), 자산이 적으면 카드가 내용에 맞춰 줄고 많으면 상한에서 잘려 스크롤바가 생긴다.

- **작업 수준 차단 / 허용(화이트리스트) 규칙 추가**: 전역 규칙과 독립적이며 해당 작업에만 적용된다. 판정 순서는 「먼저 차단, 다음 허용」 — 차단 적중이면 금지; 차단 미적중이지만 이 작업에 허용 규칙이 설정되어 있고 모두 미적중이면 「테스트 불허」; 허용 규칙이 설정되지 않았으면 화이트리스트를 활성화하지 않는다. 작업 생성 시 입력하거나 작업 상세 「개요」에서 추가·삭제·수정 및 활성/비활성할 수 있다.
- **작업 템플릿이 분류와 작업 수준 차단/허용 규칙 프리셋 지원**: 템플릿은 작업 분류와 작업 수준 규칙 묶음을 저장할 수 있으며, 템플릿 적용 시 신규 작업 폼에 함께 들어간다.

#### 수정된 문제

UI의 「테스트 자산」 뷰(작업 생산자별 필터)는 영향받지 않는다.
- **worker의 work 간 회돌이 도구가 오삭제된 문제 수정**: `search_all_worker_traces` / `get_worker_trace`(및 `node_detail`)를 worker 기본 도구 세트에 넣은 뒤, “worker 도구 면 수렴”이라는 구(舊) 마이그레이션이 시작 시 다시 언바인딩해 worker가 실제로 이 도구들을 받지 못했다. 이제 그 언바인딩 목록에서 제거하고, 구(舊) 마이그레이션을 이미 돌린 DB에는 한 번에 보충 바인딩한다.
- **`/btw` 측면 질문이 간헐적으로 DB 저장에 실패하던 문제 수정**: side_question checkpoint를 DB에 쓰기 전에 JSONB가 지원하지 않는 NUL(`\u0000`) 이스케이프를 벗겨, 이 문자를 포함한 내용의 기록 오류를 피한다.

#### 수정된 문제

- work가 **공전 회합**으로 조기 중단되는 문제 수정: 모델이 때로 한 라운드 전체를 사고 출력에만 쓰고 본문도 도구 호출도 하지 않는다. 이때 harness가 보는 것은 자연 종료(`end_turn`이고 `tool_use` 없음)이며 곧바로 `completed` + 빈 요약으로 끝낸다 — 아직 못 끝낸 의도가 한복판에서 끊기는 것으로, 「작업은 정상 종료됐는데 아무 문자 요약도 없다」로 나타난다. 5계층 LLM 재시도 중 어느 계층도 이것에 닿지 못한다. 이것은 오류가 아니고, 같은 provider의 안전 창 재시도 입구는 "스트림 실패"이며, 서킷브레이커는 `err == nil`이면 성공으로 판정하고, 의도 재실행은 `model_error`만 인정한다. SDK의 빈 응답 재시도도 닿지 못한다 — 그 계층은 "이벤트를 yield한 적이 있는가"로 공판정을 내는데, 사고 증분 자체가 이벤트이기 때문이다. 이제 work의 Stop 훅이 이런 회합을 식별해 이어달리기 지시문을 주입해, 모델이 이미 산출한 사고를 가지고 다음 단계를 계속 실행하게 한다 — "그대로 재전송"은 의도적으로 선택하지 않았다. 이런 공전은 보통 프롬프트와 컨텍스트 형상이 정하는 안정적 행동이지 무작위 발작이 아니므로, 재전송은 모델에게 다시 한번 생각하게 할 뿐이다.
- 횟수는 LLM 페이지 「재시도와 백오프」의 **빈 응답 재시도 횟수**를 재사용한다(둘 다 "모델이 끝냈는데 실질 내용을 산출하지 못함"에 답하며, 판정 기준과 수단만 다르다). 기본 2회, `-1`을 넣으면 끄고 기존 "공전하면 그대로 마무리" 행동으로 돌아간다. 이것은 연속 횟수가 아니라 한 의도의 **총량** 상한이다. harness 자체가 연속 공전은 한 번만 밀도록 제한하고, 실제로 도구 회합이 있었을 때만 배당을 갱신하므로, 이 숫자가 막는 것은 「도구 → 공전 → 밀기 → 도구 → 공전」류 순환으로 의도 예산을 소진하는 것이다. 트리거 시 로그는 `[work <worker> · #<意图>] 空转回合…注入续跑指令 (n/N)`로 남긴다. 설계는 `docs/LLM重试设计.md` §1.1 참조.
- 긴 대화에서 `/btw`의 컨텍스트 예산과 입력 레이아웃 수정; 비안전 컨텍스트(비 HTTPS 접근)에서는 측면 요청 ID를 저등급 방식으로 생성.

- 수호 시작 스크립트 `start.sh` / `start.bat`가 정식 시작 입구로 신설(릴리스 패키지와 Docker 이미지에 모두 포함, `install.sh`는 변동 없음). 종료 코드로 다시 띄울지 결정하고 SIGTERM을 artex로 전달한다. 검증과 갈아입기 로직은 모두 Go 안에 있고 스크립트는 단순하게 유지한다.
- 실패 자동 폴백: 검증이나 스모크를 통과하지 못하면 버리고 현재 버전으로 계속 실행한다. 신버전이 연속 3회 시작에 실패하면 이전 버전으로 롤백한다. 설정 페이지에 별도 수동 롤백이 있다(DB 구조는 롤백되지 않음에 주의).
- 업데이트는 GitHub 도메인만 인정하고 HTTPS를 강제하며 릴리스 출처는 설정 불가. 개발 빌드는 원클릭 업데이트를 비활성화한다. GitHub 질의 결과는 30분 캐시해 상단바 안내가 API 할당량을 소진하지 않게 한다.

#### 알려진 제한

- Docker에서는 프로그램만 바뀌고 이미지는 바뀌지 않는다. 도구 체인이 함께 업그레이드되지 않으며, 컨테이너를 재생성하면 이미지 기본 버전으로 돌아가므로 필요 시 여전히 `docker compose pull artex`를 쓴다.
- 릴리스 패키지의 `skills/`를 동기화하지 않는다. 신버전에 새로 추가된 내장 skill은 자동으로 유효화되지 않는다.
- 업데이트는 곧 재시작이며 실행 중인 작업을 중단시킨다.

### LLM

#### 새로운 기능

- LLM 페이지에 「재시도와 백오프」 탭 신설: 5계층 재시도의 **횟수**와 **간격**을 모두 설정할 수 있다. 한 번의 모델 호출 실패는 안쪽에서 바깥쪽으로 연결 재시도(SDK, 스트림 시작 전 연결 리셋 / 타임아웃 / 429 / 5xx), 빈 응답 재시도(SDK, 정상 종료였는데 아무 내용도 없음, openai 형식에만), 같은 provider 안전 창 재시도(호출자에게 어떤 출력도 전달하기 전의 단절 스트림 재생), 폴링 서킷브레이커(연속 실패가 임계에 이르면 냉각·건너뜀), 의도 재실행(worker가 model_error로 끝나면 의도 전체를 다시 실행)의 5계층을 거치며, 안쪽 계층을 다 써야 바깥 계층으로 넘어간다. 계층마다 두 개의 노브가 있고 의미는 통일이다. 비움 = 기존 기본 횟수와 지수 백오프 사용; 횟수를 채우면 그 횟수 사용; 간격을 채우면 지수 백오프를 고정 간격으로 교체; -1 = 이 계층 재시도 끔. 앞의 세 계층은 엔드포인트를 따라가며 모델 설정마다 필드 단위로 전역 기본값을 덮어쓸 수 있다(간격만 고정한 것은 여전히 전역 횟수를 상속). 서킷브레이커와 의도 재실행은 프로세스 수준 의미라 전역 한 벌뿐이다. 저장 후 핫 적용되며 재시작이 필요 없다. 전부 비우면 현재 행동 그대로이고, 구(舊) DB 업그레이드 후에도 바이트 단위로 변하지 않는다(신규 컬럼 기본 0, settings 키가 없으면 전부 기본). 연결 테스트는 의도적으로 이 파라미터를 실지 않는다 — 30s 하드 타임아웃이 있어 사용자가 설정한 재시도를 얹으면 쓸 수 있는 엔드포인트를 타임아웃 실패로 측정할 뿐이다. 설계는 `docs/LLM重试设计.md` 참조.
- 각 LLM 설정이 커스텀 **세션 헤더**(`session_header_key`) 지원: 비어 있지 않으면 매 LLM 요청에 이 HTTP 헤더를 붙이고, 헤더 값은 현재 실행의 session id(chat 세션은 `conv-<id>`, worker는 `exp<x>-worker-i<intent>` 등)다. session-id 헤더로 프롬프트 캐시 / 스티키 라우팅을 하는 일부 게이트웨이를 위해 쓴다. 구현상 요청 context에서 session id를 읽어 주입하며 norma를 고칠 필요가 없고, 같은 공유 provider라도 세션별로 다른 헤더 값을 보낼 수 있다. 구(舊) DB는 마이그레이션을 동반하고, 프런트 LLM 설정 팝업에 입력창이 추가된다.

#### 수정된 문제

- LLM 설정 저장 시 세션 헤더 필드가 비면 `23502`를 곧바로 내뱉던 문제 수정: 이 컬럼은 `NOT NULL DEFAULT ''`인데, 이전에 `NULLIF($n,'')`을 잘못 씌워 미작성 세션 헤더를 NULL로 써 비-NULL 제약을 트리거했다. 이제 빈 문자열 의미로 직접 전달한다.

### Agent

#### 새로운 기능

- 벽시계 타임아웃이 **현장 마무리**로 변경: norma v0.3.6에 의존하며, `MaxDuration`이 도달하면 실행 중인 도구를 끊고 살아 있는 ctx 위에서 마무리 라운드 수만큼 계속 실행한다(이미 식별된 내용 기록 + 요약, 종료 상태는 timeout). worker/planner 각자의 `maxDur+90s` 외부 하드 ctx가 막힌 run을 `aborted_tools`로 바로 죽이던 방식에 더 이상 의존하지 않는다. chat은 같은 harness를 거쳐 자동으로 같은 행동을 얻고, mainagent는 `MaxDuration`이 없어 영향받지 않는다.
- 정지 폴백: planner가 하트비트 / 무변동으로 깨어났는데 그래프에 open이나 running 의도가 더 이상 없을 때, 오프닝이 정지 경보로 바뀌어 명확히 고한다 — 실행 중인 worker가 없고 대기 방향이 없으며, 이번 라운드는 서로 중복되지 않는 새 의도를 하나 이상 산출해야 한다(0 의도 산출 불가).

#### 변경된 기능

- worker 프롬프트 재구축: 의도 / 시작 지시 / 앵커 자산 원본 JSON을 system prompt로 옮기고 매 라운드 다시 조립해 compaction에 눌려 없어지지 않으며, 이어달리기도 transcript 첫 메시지 보존에 의존하지 않는다. 시작 user 메시지는 전역 상황 overview만 담도록 슬림화(강등 가능, stale 허용). 대가로 system에 per-intent 데이터가 섞여 의도 간 캐시 재사용을 잃는다 — 「의도를 잃지 않기」 위한 의도적 선택이다.
- planner / worker 기본 본문 경량화 및 실전 문제 몇 가지 수정: planner는 `recent_done`을 상태별로 구분하고(blocked/exhausted는 먼저 trace를 본 뒤 결정, 막힌 길로도 무뇌 재실행으로도 취급하지 않음), 부정 결론은 「관찰 / 의심, 확정 아님」으로 바꾸고 채택 전 evidence를 보며, 목표 미달성인데 open/running 의도가 없으면 반드시 산출한다(하드 하한), 깊이가 커버리지보다 우선이다. worker의 부정류 결론은 「관찰 + 시험적 해석」만 쓰고 판결권은 planner에게 두며, 의도 간 단서는 fact의 summary에 넣어 Planner에게 넘기고 스스로 추구하지 않는다. reseed는 새 기본값을 새 버전으로 추가하고 그쪽으로 전환하며, 사용자 커스텀 / 구(舊) 버전은 이력에 남아 롤백 가능하다.
- work agent 기본 도구 세트와 자산 기록(write-back) 프롬프트 수렴: worker는 단일 의도의 실행과 기록만 담당하고, 컨텍스트 읽기 / work 간 복기는 계획 책임이므로, 기본 도구에서 `list_facts` / `node_detail` / `list_companies`와 work 간 검색(`search_all_worker_traces` / `list_worker_traces` / `get_worker_trace`)을 제거하고 `list_findings`(취약점 보고 전 중복 확인) + `add_finding` / `record_fact` + `insert_assets` / `list_assets`만 남긴다. 프롬프트에서 `insert_assets` 스키마와 충돌하는 낡은 필드 설명(`type=tech`/`on_url`/`props`)을 삭제했다. 구(舊) DB는 일회성 마이그레이션으로 해당 바인딩을 떼어내며, planner/main의 같은 이름 바인딩은 건드리지 않는다.

### 탐색 그래프

#### 새로운 기능

- **탐색 그래프 콜드 노드 압축(cold-digest)**: 오래되고 장기간 비활성인 의도 / 사실을 digest 노드로 접어 `graph_overview`에 표시한다. 원본 노드는 영구 보존되고 id로 완전 복원 가능하다(저장 무손실, 표현만 압축, 접기 가역). 냉열 판정은 역방향 도달 가능성 + 활성 분기 하나라도 있으면 뜨겁다고 보며, R=6 라운드 디바운스와 연결 성분 그룹핑을 곁들인다. 백그라운드 압축(minor는 미커버 콜드 블록 접기, major는 원본으로 돌아가 재압축해 파편 병합)은 활동도 재확인과 냉각 상호배제를 갖추고, 절대 핫 경로에 오르지 않으며 이미 부활한 노드를 덮어쓰지도 않는다. 개요 쪽은 `cold_digests`와 자산 색인 `cold_index`를 제공하고, `expand_digest` / `expand_index`가 복원을 담당한다. 연관 / 상속 작업의 개요도 그 자체 접힘 뷰를 재사용하며, `expand_digest`는 작업 간 읽기 전용 복원을 지원한다. `expand_digest` / `expand_index`는 planner와 main agent에만 주어지고 worker에게는 주지 않는다. 모두 구(舊) DB 마이그레이션을 동반한다.
- `graph_overview`가 `finding_list`를 전량 출력: findings는 작업의 최고 가치 산물이고 단일 작업에서 보통 많지 않으므로, 개요에서 전량 실어 보낸다(facts처럼 최근 창만 주는 게 아니라). planner/worker는 매 라운드 모든 확정 취약점을 한눈에 다 보고 `list_findings`를 다시 호출할 필요가 없다. 각 항목은 `{id, summary, evidence?, from_intent?, assets?}`로 경량화되며, 영향받은 자산은 나중 id가 아니라 읽을 수 있는 내용(url / 도메인 / ip:port)으로 준다.

#### 변경된 기능

- `graph_overview`가 더 이상 `hosts`를 평평하게 펼치지 않는다. coverage 블록에서 host 목록을 제거했다(대범위 작업에서 라운드마다 host 문자열 최대 500개를 실어 다니는 것은 계획 판단 가치가 제한적), `host_count`만 남기고 구체적 호스트는 필요 시 `list_assets`로 조회한다. 최상위에 `done_intents_total`(종료된 의도 총수)을 신설해 ≤15로 잘린 `recent_done_intents`와 나란히 두어, planner가 중복 제거할 때 잘렸는지 여부를 안다.

### LLM

#### 새로운 기능

- 모델 설정에 「출력 상한」 신설, 상한에 쓸 요청 필드 이름도 선택 가능: 상한은 한 번의 회신이 최대 몇 token을 생성할지 제한하며 매 요청에 실려 나간다. 0(기본) = 이 필드를 보내지 않고 서버 기본값에 맡김. 「컨텍스트 창」과는 두 가지 문제다 — 후자는 모델의 총 용량으로, 로컬에서 압축 임계값 계산에만 쓰이고 요청에는 나오지 않는다. 필드 이름 스위치는 `openai`(Chat Completions) 형식에만 의미가 있다. 빈 값(기본)은 `max_tokens`를 보내며 대부분의 호환 게이트웨이는 이것만 인정한다. OpenAI 공식 추론 모델(o 시리즈 / GPT-5)은 반대로 `max_completion_tokens`만 인정하고 `max_tokens`를 받으면 `unsupported_parameter`를 곧바로 내므로, 이런 엔드포인트는 수동으로 새 필드로 전환해야 한다. 두 형식은 각자 필드 이름을 정해놓았다(Anthropic은 `max_tokens`, Responses API는 `max_output_tokens`) — 그래서 openai가 아닌 형식에서는 이 스위치가 회색으로 비활성되고 저장 시 비운다. 아울러 지금껏 한 번도 연결되지 않은 체인을 보충했다. planner / worker / chat / 메인 Agent / 목표 분해 5곳은 출력 상한을 설정한 적이 없었고, openai 계열은 아예 보내지 않고 Anthropic은 SDK의 8192 폴백을 쓴다 — 설정 항목만 늘리고 이 체인을 잇지 않으면 숫자를 넣어도 효과가 없다. 이제 값 산출이 「스트리밍 출력」과 마찬가지로 설정별로 매 라운드 파싱되어, 페일오버 전환 후 다음 라운드부터 효과가 있다. 구(舊) DB 업그레이드 후 행동은 완전히 변하지 않는다(신규 컬럼 기본 0과 빈 필드 이름).
- 백그라운드에서 「테스트」를 누를 때 매 HTTP 시도의 상태 코드와 게이트웨이 원본 응답 본문을 서버 로그에 넣는다(응답 본문은 4K로 절단). 401, 할당량 안내 문구, 빈 프레임, HTML 페이지 반환 등의 진단에 쓰이며, UI가 접은 ok / err만 보던 때와 다르다. 이 로그는 「LLM 기록」 스위치에 의존하지 않는다.

#### 변경된 기능

- 작업 LLM 설정 체인이 어떤 상태에서든 수정 가능하도록 바뀌어 「실행 중 / 일시정지 / 설정 체인 소진」 제한이 사라짐: 작업 종료(done / failed / timeout) 후에도 메인 Agent 대화는 여전히 이 체인을 따르고, 체인의 모델에 문제가 생기면 이전에는 고칠 수도 없어 계속 상호작용할 방법이 없었다. 백엔드 HTTP와 DB 트랜잭션 두 곳의 종단 상태 차단을 함께 제거했고, 프런트 팝업도 종단 상태 작업에 편집·저장을 연다. 종단 상태 작업 저장 시 더 이상 할당량 차단 의도를 다시 열지 않는다(그 의도들은 open으로 옮겨지며 worker가 실행하지도 않고 「의도 재실행」 조건도 더는 충족하지 않는다). 계속 실행하려면 여전히 의도 재실행 / 신규 목표 추가로 가며, 그것들이 작업을 다시 실행 상태로 끌어올린다.

### Agent

#### 변경된 기능

- 「실행 중인 Worker에게 메시지를 보내 방향을 조정」이 기존 일시정지 / 재개 + transcript resume 메커니즘을 재사용하도록 바뀌어 메인 Agent 대화와 행동이 일치: 이전에는 자체 개입 지속화 프로토콜을 써서 스케줄링 장벽, 복구 절차, 십여 곳의 활동 질의 필터를 건드렸다. 이제 메시지는 다음 라운드 입력으로 주입되고 의도는 전용 goroutine에서 곧바로 돌며, 3슬롯 worker 풀 제한을 받지 않고 보내는 즉시 실행된다. 프런트는 메시지 상자를 유지하고 「바로 이어가기」 버튼을 복구했으며, 전송은 SSE로 옮겨 실린다. DB 스키마 변경 없음. 선택: 메시지는 메모리에만 저장하고 크래시 복구는 하지 않으며, 메시지 전송 시 해당 작업이 순간적으로 동시성을 worker 1개 초과할 수 있다(저빈도 시나리오로 수용 가능).

### 작업

#### 수정된 문제

- 대형 작업 아카이브 시 메모리 고갈(OOM) 크래시 수정: 아카이브가 스트리밍으로 스냅샷을 기록하도록 바뀌어 작업 전체를 한 번에 메모리로 읽지 않는다. 아울러 콜드 아카이브 경로의 세 회복 구멍을 메웠다 — 현대 설치에서 트래픽은 SQLite에만 존재하는데, 이전에는 PostgreSQL 커밋과 SQLite 커밋 사이에서 크래시하면 이미 아카이브된 작업의 트래픽이 핫 스토리지에 발목 잡혀 복구할 길이 없었다. 이제 이력 디렉터리 유무와 무관하게 스테이징 로그를 쓰고, 누락된 `journal.json`도 폐기 가능한 것으로 처리한다.
- 작업이 많을 때 시스템 버벅임 수정: 대화 로드와 화면 로드에 뚜렷한 지연이 있었다. 작업 목록, 작업 컨텍스트, 탐색 기록 질의를 함께 최적화했고, 프런트의 대시보드, 대화 페이지, 작업 상세 페이지도 중복 요청을 동기적으로 줄였다.

### 자산

#### 변경된 기능

- 기업 자산 범위의 「최대 256건 규칙」 제한 제거: IP / 도메인을 하나씩 범위로 입력하는 기업은 이 상한을 쉽게 친다. 친 뒤에는 기업을 여러 개로 쪼개는 수밖에 없는데, 범위 자체는 건수가 많아져도 느려지지 않는다. 프런트·백엔드·demo mock 세 곳의 상한을 함께 제거했다. 단건 규칙은 여전히 1024자로 제한되고 요청 본문 2 MiB 상한은 폴백으로 유지한다(약 4-5만 건 규칙).

### 스킬

#### 수정된 문제

- 스킬 압축 패키지 업로드가 「업로드 실패: zip: unsupported compression」을 보고하던 문제 수정: Go 표준 라이브러리는 Store / Deflate 두 해제기만 내장해, 압축 소프트웨어가 비기본 등급으로 쓴 bzip2, Zstandard 패키지는 전부 열지 못했다. 이제 이 두 해제기를 보충한다(순수 Go 구현, 새 외부 의존성 없음). Deflate64 / LZMA / XZ / PPMd 등 정말 열 수 없는 방식과 암호화된 패키지는, 압축을 풀기 전에 중국어 안내를 먼저 내보내 어떤 파일이 어떤 압축 방식을 썼는지, 어떻게 다시 포장해야 하는지 바로 지목한다 — 밑바닥의 영문 오류를 사용자에게 넘기지 않는다.
- 스킬 내 파일명 검증이 중국어 파일명을 불법으로 판정하던 문제 수정: 경로 검증은 원래 `[A-Za-z0-9-_./]`의 ASCII 화이트리스트였고, 압축 패키지에 중국어로 명명된 파일이 하나만 있어도(`参考/说明.md` 등) 전체 패키지 업로드가 「압축 패키지에 불법 경로 포함」으로 실패했다. Unicode 블랙리스트로 바꾼다. 각종 언어의 파일명과 공백을 허용하되, 제어 문자, 불법 UTF-8, 제로 폭과 양방향 제어 문자(RLO 파일명 위장), `\ % # ? * : " < > |`, 그리고 `..` / 절대 경로 / 빈 경로 조각은 여전히 거부하며, 디렉터리 트래버설 방지 행동은 변하지 않는다. 스킬 이름도 마찬가지로 열었다 — ASCII는 여전히 소문자, 숫자, 하이픈(agentskills.io 규범)으로 제한되고, 중국어 등 비 ASCII 문자는 스킬 이름으로 직접 쓸 수 있으나 공백, 점, 경로 구분자는 받지 않는다.
- Windows 압축 소프트웨어가 만든 중국어 패키지를 푼 뒤 파일명이 깨지거나 패키지 전체가 거부되던 문제 수정: 이런 zip은 UTF-8 플래그를 세우지 않고 GBK로 파일명을 쓰므로, 이제 GBK 폴백 디코딩 후 경로 검증을 한다. 동시에 `name: "中文技能"` 같은 따옴표가 붙은 frontmatter도 스킬 이름을 올바르게 얻는다.

### UI

#### 새로운 기능

- 발견 페이지에 「전체 발견」 평면 뷰를 신설하고 기본으로 삼으며, 기존 「작업별 그룹」 뷰와 페이지 헤더 탭으로 전환한다. 그룹 뷰는 작업을 하나씩 펼쳐야 취약점이 보이고, 작업을 넘나들며 목록만 훑고 싶을 때는 오히려 우회다. 평면 뷰는 작업을 가로지르는 큰 표(페이지당 10/20/50/100건)이며 행동은 그룹 뷰와 완전히 같다 — 체크 후 내보내기, 행 내 펼침으로 증거와 상세 보고서 보기, 행 내에서 이름/분류/심각도 변경, 처리 상태 변경, 심층, 삭제. 두 뷰는 통계 카드와 필터 바를 공유하고, 전환해도 필터가 날아가지 않으며, 현재 뷰와 필터 항목은 로컬에 함께 기록한다. 폴링은 현재 뷰만 치고, 행 내 변경은 양쪽 캐시에 동기 기록되어 전환해도 낡은 데이터가 보이지 않는다.
- 발견 페이지에 「자산별」 뷰 신설: 왼쪽 자산 트리(기업 → 루트 도메인 / IP → 서브도메인 → 서비스 → 인터페이스, 기업층은 자산이 실제로 소속을 가질 때만 나타남), 오른쪽은 선택한 노드의 온 서브트리 아래 발견으로, 나머지 두 뷰와 같은 표와 같은 필터 조건을 공유한다. 트리는 발견이 있는 자산만 받고 조상 체인은 필요 시 채워 넣는다(발견이 가장 깊은 인터페이스에만 달려 있어도 위 몇 층은 마찬가지로 조립된다). 노드의 카운트는 서브트리 집계이며 발견별 중복 제거된다. 자산이 삭제되었거나 애초에 자산과 연관 없는 발견은 「미연관 자산」 버킷으로 간다. 나머지 두 뷰와 달리 자산 뷰는 폴링하지 않는다 — 뷰에 진입하거나 필터를 바꾸거나 페이지 안에서 발견을 추가·삭제·수정하거나 트리의 새로고침 버튼을 누를 때만 조회한다. 왼쪽 트리는 내비게이션 구조라 5초마다 재계산할 이유가 없다. 트리의 각 층은 이전 층 대비 증분만 표시한다(서브도메인은 루트 도메인 접미 제거, 서비스는 `https :443` 표시, 인터페이스는 경로만 표시), 완전한 값은 호버 툴팁과 브레드크럼에 있다. 노드가 너무 많으면 인터페이스/서비스 층을 통째로 버리고 안내를 주며, 카운트는 여전히 상위 층에 계산된다.

#### 수정된 문제

#### 변경된 기능

- planner 프롬프트의 「이번 라운드 0 의도」 판정 근거를 재작성: 원문은 0 의도를 「가장 흔하고 가장 중요한 원칙」으로 기술해, Planner가 목표 미달성·범위 내 미테스트 면이 남아 있는데도 너무 이르게 손을 떼게 만들었다. 이제 두 가지 구체적 상황에서만 0 의도를 산출해야 한다 — ① 생각한 방향이 모두 open/running/recent_done 의도로 이미 커버됨; ② 다음 단계가 현재 실행 중인 work의 산출에 의존하는데 산출이 아직 나오지 않음(그것이 끝나고 그래프가 갱신된 다음 깨어남에서 계획해야 함). 역방향 제약도 보충: 확실히 커버되지 않았고 실행 중 work에 의존하지 않는 새 방향이 있거나, 목표 미달성인데 미테스트 면이 남아 있으면 「0 의도는 흔하다」는 이유로 손을 떼지 말 것.
- worker 프롬프트의 「부정 결론의 증거 문턱」 강화: 「주입 불가/포트 닫힘/로그인 입구 없음」 같이 Planner가 한 방향 통째로 버리게 만들 수 있는 부정 결론은, 결론 내기 전에 해당 의도 안의 합리적 수단(인코딩/파라미터/경로/메서드 교체)을 먼저 다 쓰도록 요구한다. 수단을 다 쓰지 못했거나 증거가 약하면 일률적으로 `confidence=inferred`를 표기해, 성급한 `observed` 부정으로 전체 경로를 용접해 잠그는 일을 피한다(작업 초반의 잘못된 부정은 특히 방향을 틀어놓고 자가 치유가 어렵다).
- 위 planner / worker 기본 프롬프트 변경은 일회성 마이그레이션(`reseedPlannerPrompt` / `reseedWorkerPrompt`, 각자 settings flag 가드 포함)을 통해 새 버전으로 추가되고 현재 버전으로 전환된다. 구(舊) 버전은 버전 이력에 남아, 프롬프트를 커스텀한 적 있는 사용자는 버전 기록에서 복구할 수 있다.

#### 삭제된 기능

- Worker 다중 선택, 전체 선택, 일괄 일시정지/계속 화면을 삭제하고 Worker 일괄 제어 API와 Mock 계약도 제거했다.
- Worker 목록 행의 Token 배지와 Tooltip을 삭제했다. 밑바닥의 완전한 Token 장부와 작업 집계 API는 계속 보존된다.

### LLM

#### 새로운 기능

- 작업이 순서 있는 LLM 설정 체인 지원. 공급자 할당량 부족을 명확히 식별하면 다음 설정으로 자동 전환하고, 현재 설정, 소진 상태, 오류 요약을 지속화한다.
- 실행 중과 일시정지 작업이 완전한 설정 체인 편집, 순서 조정, 현재 설정 수동 전환을 지원하며 다음 LLM 호출부터 효과가 있다.
- 자동 전환, 수동 전환, 전 체인 소진이 구조화된 시스템 활동으로 기록되고 작업 활동 스트림을 통해 중복 제거 가능한 알림으로 뜬다.
- 작업 역할 모델 해석 API 추가: 메인 Agent, Planner, Worker의 다음 호출에 쓰일 설정과 모델을 통일 해석한다.
- 선택 가능한 전역 LLM Pool 추가: 호출 순서 설정, 지정 모델 실패 폴백, 건강 상태, 냉각 복구, 수동 리셋을 지원한다.
- 항상 켜져 있는 LLM 사용량 장부 추가: 작업, 세션, 모델, 설정별로 입력, 출력, 캐시 Token을 집계한다.

#### 변경된 기능

- 목표 분해, Planner, Worker, 메인 Agent가 작업 수준 LLM 런타임을 공유한다(해석 우선순위는 아래 참조).
- 페일오버는 명확한 할당량, 잔액, 청구 오류에만 응답한다. 일반 속도 제한, 인증, 네트워크, 서버측, 컨텍스트 오류는 잘못 전환하지 않는다.
- LLM 설정 페이지가 설정 카드 목록 + 오른쪽 드로어 편집으로 바뀌고, Pool 폴링 순서, 우선순위, 제외 항목, 건강 상태, 복구 조작을 제공한다.
- 설정 체인 소진 정보가 좁은 화면에서 줄바꿈을 지원한다. 현재 모델은 세션 목록 아이콘에서 현재 세션 제목 옆의 문자 라벨과 완전한 Tooltip으로 바뀐다.
- 작업 내 각 역할이 LLM을 해석하는 순서가 「Agent 바인딩 → 작업 설정 체인 → 전역」으로 조정되었다. 명시적으로 모델을 바인딩한 역할은 늘 그 모델로 실행되고, 바인딩하지 않은 역할만 작업 체인으로 떨어지며, 작업 체인이 비면 다시 전역으로 떨어진다.
- 출구 프록시를 비우면 직결되며 `HTTP_PROXY`/`HTTPS_PROXY` 환경변수로 더는 폴백하지 않는다(명시적 `ARTEX_LLM_PROXY`는 영향받지 않음). 프록시 입력은 계정·비밀번호가 붙은 `socks5://user:pass@host:port`를 지원한다.

#### 수정된 문제

- 제출 전(어떤 출력도 산출하지 않은) 순간 스트리밍 실패가 같은 provider에서 안전 백오프 재시도하도록 해, 「도구 한두 개만 돌고 중단, 요약 없음, 종료 상태 `model_error`」 상황을 크게 줄였다. 할당량 소진, 컨텍스트 과장, 4xx 결정론적 오류는 재시도하지 않고 여전히 각각 페일오버와 압축 복구로 넘긴다.

#### 삭제된 기능

- 세션 목록의 LLM 아이콘 표시를 삭제해 Worker 상태 아이콘과의 혼동을 피한다.

### UI

#### 새로운 기능

- 작업이 전역 분류 생성, 이름바꾸기, 삭제, 필터링을 지원한다. 신규 작업에서 분류를 직접 선택할 수 있다.
- 전역 작업 템플릿 CRUD와 오른쪽 관리 드로어 추가. 신규 작업은 프리셋 설명과 목표를 불러올 수 있고, 현재 내용을 템플릿으로 다른 이름 저장할 수도 있다.
- 신규 작업이 여러 출처 작업과 여러 기업 자산 범위 연관을 지원한다. 기업 범위는 단일 다중 행 텍스트상자로 도메인, URL, IP, CIDR, ICP, 기업 키워드를 자동 인식한다.
- 작업 테스트 자산이 실시간 추가·삭제를 지원하고 인간, 기업, 상속, Agent 발견 등 출처를 기록한다. Worker 세션 제목 옆에 현재 테스트 자산과 출처 요약이 표시된다.
- 발견 페이지가 작업별로 그룹핑되고 그룹 내 독립 페이지네이션을 제공하며, 취약점에 설명을 적고 고우선순위 심층 의도를 만들 수 있다.
- 대화가 이름바꾸기, 고정, 고정 해제, 삭제를 지원한다. 작업 목록은 현재 페이지 일괄 일시정지와 계속을 지원한다.
- 트래픽 상세와 도구 실행 상세가 오른쪽 드로어로 바뀌고, HTTP 패킷에 `Host`를 보완해 요청행, 상태 코드, Header, JSON, 마크업 언어 본문을 하이라이트한다.
- 작업 목록 조작 열에 「상세」와 「일시정지/계속」 버튼 추가. 세션 전송 키 배치는 시스템 설정에서 설정 가능(`Enter` / `Cmd+Enter` 등)하고 Web 검색 영역에 프록시 입력창이 추가됐다.
- 세션 제목 오른쪽 배지가 LLM 설정 이름을 표시하도록 바뀌고, 모델 ID는 hover Tooltip으로 옮겨졌다. 작업에 선택적 이름을 설정할 수 있고 작업 목록에 이름 열과 검색이 추가됐다(비면 설명으로 폴백).
- 스킬 페이지에 사용 횟수, 최근 사용 시간, 누락 의존성 통계를 추가해 유효화되지 않았거나 미설치인 스킬을 찾기 쉽게 했다.

#### 변경된 기능

- 작업 제목이 포커스 가능한 상세 링크로 바뀌고, 작업 자산, 기업 자산, 발견 작업 그룹과 그룹 내 취약점은 서버측 실제 페이지네이션, 안정 정렬, 정확 총수를 사용한다.
- 신규 기업 추가가 오른쪽 드로어로 바뀌고, 범위 입력은 다중 행 텍스트로 통일되어 실시간 인식, 검증, 유형 미리보기를 제공한다.
- 메인 Agent 입력창이 자동 성장, `Enter` 전송, `Shift+Enter` 줄바꿈을 지원하고 중국어 입력기 조합 상태의 오전송을 피한다.
- Agent 미리보기, 작업 보고서와 관련 상세가 공유 Markdown 렌더링으로 통일되었다. 삭제 확인, 긴 오류, 모바일 드로어 폭을 통일 수정했다.
- 작업 템플릿 선택 상자가 템플릿 이름으로 표시·검색하고 템플릿 ID로 제출한다. 시스템 원본 글자 크기를 복구하고, 앱 버전을 `0.3.3`으로 통일 표시한다.
- 작업 총계와 현재 세션 Token은 입력, 캐시 읽기, 출력 수치만 하이라이트하고, 전송 버튼은 더 간결한 위쪽 화살표 아이콘을 쓴다.
- 작업 개요의 테스트 범위가 ID 대신 기업 이름을 표시한다.

#### 수정된 문제

- 점이 포함된 평범한 텍스트가 더는 ICP 등록번호로 오판되지 않는다.
- 변수 디렉터리에서 전역 런타임 변수(예: `{{.Now}}`)와 이름이 충돌해 Agent 편집기의 변수 목록이 중복 key를 렌더링하던 문제 수정.

#### 삭제된 기능

- 작업 카드의 독립 “진입” 버튼을 삭제하고 작업 제목 클릭으로 상세 진입을 통일했다.
- 대시보드의 “새 작업” 버튼, 신규 기업의 Logo URL 입력 항목, 그리고 발견 페이지 상단과 작업 그룹의 취약점 수 Badge를 삭제했다.
- 전역 글자 크기 10% 증가 스타일을 철회하고, 세션 목록의 Worker 선택 상자, 모델 아이콘, 행 단위 Token 통계를 삭제했다.

### Agent

#### 새로운 기능

- 신규 작업이 여러 기존 작업을 직접 연관 지을 수 있고, 직접 출처 작업의 목표, 사실, 취약점, 완료된 의도, 자산 범위, 블랙보드 컨텍스트를 실시간 읽기 전용 상속한다.
- 블랙보드 읽기 도구가 출처 작업의 노드, 사실, 취약점, 실행 궤적을 필요에 따라 조회하도록 지원한다. 상속 노드에는 출처 표식이 붙고 모든 쓰기 도구는 수정을 거부한다.
- 기업 범위 도구가 도메인, URL, IP, CIDR, ICP, 기업 키워드를 지원한다. 키워드는 Agent 범위 힌트로만 쓰이며 자산 자동 소속에는 참여하지 않는다.
- 취약점 심층 조작은 원 작업에 자산 앵커와 `derived_from` 간선이 붙은 고우선순위 인간 Worker 의도를 만든다.
- 개요에 「목표 관리」 카드가 신설되어 인간의 목표 조회, 추가, 수정, 삭제를 지원한다. 추가나 수정은 Planner에게 알리고 작업을 부활시키며, 삭제는 목표 노드를 하드 삭제(간선과 앵커 연쇄 삭제)하되 부활시키지 않는다.
- 메인 Agent가 기본으로 `steer_work` 도구를 얻어, 실행 중인 Worker에게 실시간으로 궤도 수정 지시를 주입할 수 있다. 중단도 진행 소실도 없다(여전히 의도가 본 작업에 속하는지 검증).

#### 변경된 기능

- 출처 작업의 의도는 신규 작업 frontier에 들어가지 않고, 신규 작업은 계속 독립 exploration, 실행 큐, 작업 디렉터리, 대화 이력을 사용한다.
- 실행 중인 의도 삭제가 더 이상 데이터를 파괴하지 않는다: `stopped`로 정지하고 삭제 사유 작성을 요구하며, 사유를 사실로 해당 의도에 붙이고 payload에 기록한다. Planner는 `cancelled` 트리거로 감지한다(의도 내용과 사유는 보존).
- 메인 Agent 대화가 서버측 활동 스트림 구동으로 바뀌어, 전송 실패 시 입력을 복구할 수 있다. 세션을 열면 자동으로 맨 아래로 붙고 상세 지연 로드 후에도 마지막 회답이 보이게 유지한다.
- 작업 일시정지는 현재 Main Agent, Planner, Worker 호출을 종료하지만, 일시정지 중 사용자가 새로 메인 Agent 오케스트레이션 세션을 시작하는 것은 막지 않는다.
- 취소, 종료, 스트리밍 중단이 실제 종료 사유, 이미 생성된 내용, 실행 라운드 수, 소요 시간, Token과 미반환 도구 호출을 통일 보존한다.

#### 삭제된 기능

- 메인 Agent 클라이언트의 낙관적 메시지 회돌이를 삭제해, 일시정지, 실패, 동시 활동에서의 중복 메시지와 세션 간 섞임을 피한다.

### 제약

#### 새로운 기능

- 목표 분해 단계에서 먼저 운영 제약(allow/deny)을 뽑은 뒤 목표를 분해하고, 메인 Agent 실행 중에 보충할 수 있다. 제약은 최고 우선순위로 Planner와 Worker 시스템 프롬프트에 주입되어, 편향 제거 후의 다양성·면 확장 탐색이 명시적으로 제약에 복종한다.
- 개요에 「제약 관리」 카드와 추가·삭제·수정 API 신설. 제약 주입 범위는 Planner / Worker별로 각각 켜고 끌 수 있다(기본 둘 다 켬, 라운드마다 읽고 즉시 효과). 신규 테이블 `task_constraints`는 `CREATE TABLE IF NOT EXISTS`를 사용해 구(舊) DB가 자동 보완 생성한다.

### 차단

#### 새로운 기능

- 명령 차단이 정규식/문자열 규칙 외에 모델 폴백 승인 신설: 규칙 하나도 적중하지 않으면 모델이 `ALLOW`/`ASK`/`DENY` 의미 판정을 하고, 실패 폴백 조치와 승인 타임아웃 조치는 설정 가능하다. 차단 페이지는 「차단 규칙 / 모델 설정」 두 Tab으로 나뉘며, 모델 판정 결과에는 `[模型]` 접두와 사유가 표기된다.

#### 수정된 문제

- 심판 출력 파싱을 강화해 올바른 `DENY` 판정이 통과로 오인되지 않게 한다.

### 트래픽

#### 변경된 기능

- 트래픽 녹화가 exchange 통째로 SQLite에 기록되도록 바뀌었다(큰 본문은 hash로 중복 제거되는 blob 버킷으로 넘친다). 텍스트 본문에 trigram 전문 인덱스를 만들어 임의 부분 문자열과 중국어 검색을 지원한다. 삭제는 단일 SQL 트랜잭션으로 퇴화해 수시간에서 밀리초급으로 내려가고, 그 동안에도 녹화가 정지하지 않는다. 대용량 body 스트리밍 다운로드와 `traffic_search` 전문 파라미터를 신설했다. 구(舊) 파일 트리 데이터는 마이그레이션 불필요하며 여전히 읽기·검색·삭제 가능하다.

### 작업과 자산

#### 새로운 기능

- 작업 생성에 「자산 커버리지 기능」 스위치 신설(기본 켬): 끄면 커버리지를 계산·표시하지 않고, 상황 그래프는 자산만 표시하며, `task_scope`를 자동 누적하지 않고, 관련 도구를 Planner / 메인 Agent에서 제거한다. 기업 연관은 이 스위치의 영향을 받지 않는다.
- `insert_assets`의 자산별 `related` 표식 신설(기본 `true`): 커버리지를 켰을 때만 효과가 있고, `false`는 공유 자산 라이브러리에만 들어가고 본 작업 커버리지에 계상되지 않는다(부수적으로 발견한 옆 사이트나 무관 자산 등).
- 기업 범위와 작업 테스트 자산이 도메인, URL, IP, CIDR, ICP, 키워드 텍스트 인식을 통일 지원한다. 도메인/IP는 전역 자산을 만들거나 재사용할 수 있고, CIDR/ICP/키워드는 작업 범위 컨텍스트로 남는다.

### 빌드

- `build.sh --release`가 Linux amd64/arm64, macOS amd64/arm64, Windows amd64를 한 번에 빌드하고 `skills/`, 설정 예시, README가 들어간 zip 릴리스 패키지를 생성한다.
- Go linker로 디버그 정보를 제거하고 zip 릴리스 패키지를 생성한다. UPX는 명시적 선택 항목으로 바뀌어, 그 자체 해제 ELF가 일부 Linux 환경 시작 때 세그먼트 오류를 내는 일을 피한다.
- Release Workflow가 Linux amd64 바이너리에 시작 스모크 테스트를 실행하고 릴리스 패키지와 함께 `SHA256SUMS`를 제공한다.

## [0.3.2] - 2026-08-20

### Added

- 신규 작업이 여러 기존 작업 연관 지원, 직접 출처 작업의 사실, 취약점, 완료된 의도, 자산 범위, 블랙보드 컨텍스트를 실시간·읽기 전용 상속. 신규 작업은 여전히 독립 실행 큐, 작업 디렉터리, 세션 이력을 사용한다.
- 작업이 순서 있는 LLM 설정 체인 지원. 공급자 할당량 부족을 명확히 식별하면 다음 설정으로 자동 전환하고, 현재 설정, 소진 상태, 구조화된 감사 활동을 지속화한다.
- 실행 중과 일시정지 작업이 LLM 설정 체인 편집, 순서 조정, 현재 설정 수동 전환을 지원한다. 자동 전환, 수동 전환, 전 체인 소진은 작업 상세 페이지에서 안내된다.
- 실행 중인 Worker가 일시정지, 재개, 취소를 지원한다. 일시정지는 블랙보드 데이터를 보존하며, 취소는 Worker가 기록을 멈춘 뒤 해당 의도와 그 직접 산출인 사실, 취약점, 실행 기록을 트랜잭션적으로 청소한다.
- 작업 삭제 시 연관 자산, 트래픽, 취약점, 작업 착지 파일을 함께 청소할 수 있고, 삭제 장벽, 동시성 보호, 감사 가능한 삭제 통계를 추가했다.
- 선택 가능한 작업 동시성 상한 추가. 상한에 도달한 신규 작업은 FIFO로 대기하고 실행 슬롯이 풀리면 자동 시작된다.
- 작업 자산 페이지네이션, 회사 자산 페이지네이션, 작업 분류 통계, 페이지네이션 의도 Mock 계약 추가.
- `build.sh` 단일 바이너리 빌드 스크립트 추가. 정적 프런트 내보내기, 리소스 임베드, 크로스플랫폼 대상, 빌드 버전 주입을 지원한다.

### Changed

- 작업 수준 명시적 LLM 설정 체인이 기존 전역 LLM Pool과 공존한다. 명시적 체인은 엄격한 할당량 페일오버 의미를 계속 채택하고, 명시적 체인이 없으면 Agent 바인딩과 전역 설정 규칙을 따른다.
- 메인 Agent 입력창이 자동 성장하는 다중 행 입력을 지원하며, `Enter` 전송, `Shift+Enter` 줄바꿈, 중국어 입력기 조합 상태의 오전송을 피한다.
- Planner, Worker, 메인 Agent가 작업 수준 LLM 런타임을 공유한다. 작업 체인은 후보 모델 중 최소 컨텍스트 창을 안전 압축 임계값으로 쓴다.
- 작업 상세 페이지가 실제 LLM 호출 상태에 따라 실행, 유휴, 일시정지 상태를 표시한다. 출처 작업의 사실, 취약점, 의도, 자산 참조, 그래프 노드는 출처 표식을 통일 붙이고 읽기 전용을 유지한다.
- Agent 미리보기, 작업 보고서와 관련 상세 뷰가 공유 Markdown 렌더링 컴포넌트로 통일되었다.
- LLM 모델 설정이 카드와 드로어 상호작용을 채택하고, 모델 목록은 드로어 안에서 독립 스크롤을 지원한다.
- 작업 일시정지가 더 이상 메인 Agent 대화를 차단하지 않는다. 메인 Agent 오케스트레이션 세션은 작업 일시정지와 독립되어, 일시정지 중에도 새 메시지를 계속 보낼 수 있다(일시정지는 현재 진행 중인 그 한 라운드만 종료).
- Worker 단일 run의 벽시계 기본 시간을 600초에서 1200초로 조정했다.

### Fixed

- 메인 Agent 콘솔의 낙관적 회돌이를 제거하고 순수 서버측 데이터 렌더링으로 바꿔, 일시정지나 전송 실패 등 시나리오에서의 메시지 꼬임, 다른 세션 내용 끼어들기를 수정했다.
- 메인 Agent 세션을 열 때 기본으로 맨 아래로 스크롤하고 마지막 회답을 온전히 표시한다. 마지막 회답의 완전한 내용은 지연 로드 펼침 후 자동으로 맨 아래에 붙고 더는 화면 밖으로 밀려나지 않는다.
- 작업 일시정지 후에도 메인 Agent 세션이 계속 돌고, 오케스트레이션 Agent가 작업을 일시정지할 때 메인 Agent를 동기 정지하지 않는 문제를 수정했다.
- 작업 완료, Planner, Worker, 메인 Agent 실제 실행 시 작업 상태 배지와 조작 버튼 상태가 동기화되지 않던 문제를 수정했다.
- Worker 취소, 작업 삭제, 동시 기록 사이에서 늦은 블랙보드 기록이나 잔여 파일이 생길 수 있는 문제를 수정했다.
- Markdown 미리보기 실효, 삭제 확인 장문 오버플로, 모바일 폭, 일부 작업 상세 버튼 미정렬을 수정했다.
- 모든 Agent 취소 경로에 명명된 종료 사유를 추가했다. 활동 상세는 취소자, 종단 상태, 실행 라운드 수, 소요 시간, Token 사용량과 미반환 도구 호출을 표시할 수 있다.
- 백엔드 종료 시 부모 context가 명명된 `shutdown` 사유를 선점 덮어쓸 수 있는 경쟁 상태, 그리고 중국어 활동 요약의 바이트 단위 절단으로 인한 깨짐 문제를 수정했다.
- 부분 스트리밍 출력이 있는 취소 이벤트가 실제 종료 사유를 잃는 문제를 수정했고, 취소 전에 생성된 내용은 보존된다.
